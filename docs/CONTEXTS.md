# Dev contexts

Keep each organisation's editor login and Claude Code login separate, chosen by
which folder you are in. `c` stays the only launcher.

## How it works

An org folder under `~/Projects` holds a one-line `.envrc`:

```bash
dev_context acme code      # or: dev_context acme cursor
```

When you `cd` anywhere below it, direnv exports:

| Variable               | Value for `dev_context acme code` |
| ---------------------- | --------------------------------- |
| `WORK_CONTEXT`         | `acme`                            |
| `DEV_EDITOR`           | `code`                            |
| `EDITOR_USER_DATA_DIR` | `~/.vscode-acme` (or `~/.cursor-acme`) |
| `CLAUDE_CONFIG_DIR`    | `~/.claude-acme`                  |

It also unsets `ANTHROPIC_API_KEY`, because an API key beats subscription login.

`c` launches the editor with `--user-data-dir`. Each user-data-dir is a separate
editor instance with its own login, and it keeps the environment it was launched
with. That is how `CLAUDE_CONFIG_DIR` reaches the Claude extension.

A folder with no `.envrc` is personal: plain VS Code, default user data,
`~/.claude`. Nothing is exported for personal. If direnv is missing, everything
is personal.

An editor started from the Dock or Spotlight is always the personal instance.
Isolated instances only start through `c`.

## What lives where

| What | Where |
| ---- | ----- |
| `dev_context` function | committed, `direnv/dev-context.sh`, linked into `~/.config/direnv/lib/` |
| Launcher `c` and diagnostic `dev-context` | committed, `functions.zsh` |
| Setup script `dev-context-init` | committed, `bin/` |
| Claude baseline settings (see [AGENT-POLICY.md](AGENT-POLICY.md)) | committed, `claude/settings.json` |
| `.envrc` files | local, hand-written, never committed |
| `~/.vscode-<name>`, `~/.cursor-<name>`, `~/.claude-<name>` | generated by `dev-context-init` |
| Editor and Claude logins | manual, once per context |

Shared across all instances of an editor: settings, keybindings, tasks, and
snippets (symlinked from `vscode/`), and extensions (the default extensions
dir). Not shared: logins, window state, extension state.

## Add a context

```bash
mkdir -p ~/Projects/acme
echo 'dev_context acme code' > ~/Projects/acme/.envrc
cd ~/Projects/acme && direnv allow
dev-context-init
c
```

In the new window, open the Claude panel and log in with that org's account.
For a Cursor context, also log in to Cursor itself, and set Cursor Settings,
Agents, Approvals & Execution to **Allowlist**. In the default Auto-review mode,
Cursor's AI reviewer can rerun a blocked command outside the sandbox without
asking you. The run mode is stored per instance, so no shared file can set it.

Trust the org folder once per instance: run "Workspaces: Manage Workspace
Trust" and add it. The Claude extension doesn't run in Restricted mode.

A second Cursor identity is the same thing with `cursor` as the editor. Nothing
in `c` or this repo changes.

To move an org to the other editor, change the word in its `.envrc`, run
`direnv allow`, then `dev-context-init`. The old user-data-dir stays until you
delete it.

## Check what is active

```bash
dev-context
```

It prints the four variables, which instance the current editor terminal
belongs to, and any problem: a missing dir, a missing editor, a malformed
`.envrc`, or an API key in the environment.

To confirm the Claude extension uses the right account:

1. Run `/status` in the Claude panel and check the account.
2. Send one message, then check that a new session appeared under
   `~/.claude-<name>/projects/`.

## Details

- **Malformed `.envrc`.** A bad `dev_context` call sets `DEV_CONTEXT_ERROR`,
  and `c` refuses to launch until it is fixed. It never falls back to personal.
- **Not set up yet.** `c` refuses to launch a context whose dirs do not exist,
  so the editor and Claude never create them without the shared settings.
- **Personal Claude in a context.** Add `unset CLAUDE_CONFIG_DIR` after the
  `dev_context` line.
- **Other per-org tools.** Add lines to the same `.envrc`, for example:

  ```bash
  export GH_CONFIG_DIR="$HOME/.config/gh-acme"
  export AWS_PROFILE=acme-readonly
  export GIT_AUTHOR_EMAIL=me@acme.example GIT_COMMITTER_EMAIL=me@acme.example
  ```

  API keys for MCP servers go here too. See
  [AGENT-POLICY.md](AGENT-POLICY.md#mcp-server-keys) for a worked example.

- **A repo with its own `.envrc`.** direnv loads only the nearest one, so start
  it with `source_up` to keep the org context.
- **One-off launch in the other editor.**
  `DEV_EDITOR=cursor EDITOR_USER_DATA_DIR=~/.cursor-acme c` (run
  `dev-context-init` with those set first).
